# Google developer documentation style

Condensed from the Google developer documentation style guide
(https://developers.google.com/style). Use it for grammar, punctuation,
and formatting questions. The unslop rules in `unslop.md` take priority
where the two overlap (for example, this guide's own examples sometimes
use em dashes, but the vault house style bans them).

## Voice and tone

- Be conversational and friendly without being frivolous.
- Write for a global audience. Keep sentences short and direct so the
  text is easy to read and easy to translate.
- Write accessibly. Don't rely on color, position, or sound alone to
  carry meaning.
- Don't pre-announce features. Document what exists now, not what's
  coming.
- Avoid excessive claims and marketing hype.

## Language and grammar

- **Second person.** Address the reader as "you", not "we".
- **Active voice.** Make it clear who performs the action.
- **Present tense.** Describe behavior as it happens now.
- **Standard American spelling and punctuation.** For a spelling
  question, follow Merriam-Webster.
- **Conditions before instructions.** "To do X, do Y", not "Do Y to do
  X". "If Z, then do Y", not "Do Y if Z".
- **Contractions** are fine and keep the tone natural.
- **Avoid anthropomorphism.** Products don't "want", "think", or "see".
- **Don't overload abbreviations.** Spell out a term on first use if the
  audience may not know it.

## Punctuation

- **Serial comma.** Use it: "a, b, and c".
- **Colons** introduce a list or example. The lead-in before a colon
  should be a full clause.
- **Semicolons** join two closely related independent clauses. Prefer
  two sentences when you can.
- **Quotation marks.** Straight quotes. Put commas and periods inside
  the closing quote in American style.

## Formatting and organization

- **Headings and titles.** Sentence case. Make them descriptive and
  parallel in structure. Don't skip heading levels.
- **Lists.**
  - Numbered lists for sequential steps or ranked items.
  - Bulleted lists for sets where order doesn't matter.
  - Description (definition) lists for pairs of related items.
  - Keep list items parallel in grammar. Capitalize the first word.
- **Procedures.** Write each step as an imperative. One action per step.
  State the result when it isn't obvious.
- **Code in text.** Put code, filenames, paths, and literal values in
  code font.
- **UI elements.** Bold the names of elements the user interacts with,
  such as buttons and menu items.
- **Dates and times.** Use an unambiguous format. Spell the month or use
  an explicit format like 2026-08-24, not 8/24.
- **Numbers.** Follow the guide's numeral conventions; in general use
  numerals for 10 and above and in technical contexts.
- **Tables.** Use them for data with a clear row/column structure. Give
  every column a header.

## Linking

- Use descriptive link text that says where the link goes. Never "click
  here" or "this link".
- Make the linked phrase a meaningful noun phrase.

## Images

- Provide alt text for every informative image.
- Prefer high-resolution or vector images when practical.

## Reference hierarchy for anything not covered

1. Project-specific style (this vault's own conventions, including
   `unslop.md`).
2. This Google style summary.
3. Third-party references: Merriam-Webster for spelling, the Chicago
   Manual of Style for nontechnical style, the Microsoft Writing Style
   Guide for technical style.

## Break the rules

These are guidelines, not rules. Depart from any of them when doing so
makes the content clearer for the reader. When you do, stay consistent
within the document.
