  ### 1. What a "feature map" is
  - **Location:** `.cursor/skills/verify-<app>/features/`. It has a `README.md` index plus one file per user-facing feature. It starts with the top 3–5 features, found from routes, commands, menus and docs.
    - Source: https://github.com/cursor/plugins/tree/main/pstack/skills/create-verification-skill/references/feature-map-example
  - **What the README holds:**
    - Baseline preconditions: port, a disposable data dir per `$RUN_ID`, seeded fixtures, and a `doctor` check. It also says "Never drive an instance that was not started by this verification run".
    - Driving conventions: ARIA roles and names over CSS, and restore seeded data.
    - Proof and skip reporting: an ARIA snapshot plus a screenshot, CLI stdout/stderr/exit code, and a second read-only view of any mutation. Record the feature ID and entry point with every artifact. Do not report a skipped entry point as verified through another path.
    - A "Feature entry contract", then the feature index.
  - **Each feature file:** an H1 and a one-paragraph user-visible description, then exactly four H2s:
    1. `Sub-features`: short IDs with one line each, e.g. `create-open`, `create-save`, `create-cancel`, `create-cli`.
    2. `How to get to it (user POV)`: every entry point (toolbar button, shortcut, CLI).
    3. `Driving it with <harness>`: starts with `Preconditions:`, then labeled bullets. Each bullet pairs a user action, an exact command and the observable result, e.g. "**Save note.** … A status named `Note saved` appears".
    4. `Gotchas`, e.g. "A save status alone is insufficient proof."
  - **A richer variant** in the Benny automation adds per-feature `Stable selectors`, `States to exercise`, `Preconditions and setup`, `Evidence and cross-check`, and a completeness checklist.

  ## Research report: test-list generation for agent-driven feature work
  
  Strength key: **[S]** = primary or official source. **[M]** = secondary or vendor marketing. **[U]** = not verified, or from a search snippet only.
  
  ### Named practices and tools
  
  1. **Anthropic: "Give Claude a way to verify its work", plus the interview pattern** — Claude Code docs, best-practices page (undated; fetched 2026-10) https://code.claude.com/docs/en/best-practices **[S]**; verification-skills blog, Jul 22 2026 https://claude.com/blog/building-verification-loops-in-claude-code-with-skills **[S]**
     - **What it is:**
       - A check that returns pass or fail, gated four ways: in the prompt, `/goal`, a Stop hook, or a refuting subagent.
       - "Have Claude show evidence rather than asserting success."
       - For larger features, "interview me using AskUserQuestion" and write a spec that "end[s] with an end-to-end verification step".
       - Verification procedures are kept as skills.
     - **Pros:** Native to the tools you already use. Evidence is quicker to review than re-running the checks.
     - **Cons:** No test-list format. Verification is framed as autonomous, so nothing covers approving a test list.
     - **Fit:** High. A `test-plan` skill that runs at plan time, plus the existing CDP/Playwright skills as runners.
  
  2. **OpenAI Codex best practices** — https://learn.chatgpt.com/guides/best-practices **[S]**
     - **What it is:** Put "Done when" criteria in the prompt. For fuzzy tasks, "ask Codex to question you first".
     - The line about the final summary listing "any behavior you could not verify" came from a search snippet only **[U]**.
     - **Fit:** Same as #1. Supports listing what could not be verified as an explicit field.
  
  3. **Simon Willison: "deliver code you have proven to work" and agentic manual testing** — Dec 18 2025 https://simonwillison.net/2025/Dec/18/code-proven-to-work/ ; guide https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/ **[S]**
     - **What it is:**
       - Agents drive the real UI (Rodney is a CDP wrapper), then record notes, commands, output and screenshots with Showboat.
       - Every PR carries proof.
       - Tests should fail when the change is reverted.
     - **Pros:** Very close to your CDP evidence flow.
     - **Cons:** Generating the list or approving it is out of scope.
     - **Fit:** High as the execution and evidence half.
  
  4. **Acceptance tests generated from tickets** — VirtusLab maturity matrix, v1.3 Jun 2026 https://visdom-maturity-matrix.virtuslab.com/guides/development/acceptance-tests-from-tickets-autonomous-requirements **[M, but reasoned]**
     - **What it is:**
       - The agent derives tests from Given/When/Then acceptance criteria before any code exists.
       - A developer reviews them in about 10 minutes and confirms they fail on the current code.
     - **Pros:** Expected values come from the requirements, not from the code. Gaps in the ticket show up early.
     - **Cons:** A vague ticket produces junk tests. The abstraction level of the tests is inconsistent.
     - **Fit:** High for the acceptance half. Your tickets already have "Done When".
  
  5. **Spec-driven development: GitHub Spec Kit `/clarify` and Kiro EARS** — https://blog.lpains.net/posts/2025-12-07-deep-dive-into-speckit/ (Dec 2025) **[M]**; https://kiro.dev/ **[S]**
     - **What it is:**
       - `/clarify` asks up to 5 targeted questions, one after another, before planning. Answers go into a dated "Clarifications" section of the spec.
       - Kiro writes requirements as "WHEN X, THE SYSTEM SHALL Y" (EARS) and derives property-based tests from them.
     - **Pros:** A ready-made model of asking questions and recording the answers.
     - **Cons:** Heavyweight for small tickets.
     - **Fit:** Copy the capped, recorded clarification step, not the whole framework.
  
  6. **Kent Beck: Canon TDD "test list"** — https://newsletter.kentbeck.com/p/canon-tdd **[S]**
     - **What it is:** Step 1 is a list of test scenarios. You turn one item at a time into a test, and add to the list as you go.
     - **Pros:** The list is a living document, which validates "dev adds edge cases".
     - **Cons:** Unit-level, with no review step.
     - **Fit:** Conceptual backing for the list as the main artifact.
  
  7. **Turborepo `--affected`** — https://turborepo.dev/docs/reference/run **[S]**
     - **What it is:**
       - Package-level diff against `main...HEAD`, including dependents.
       - Task-level selection is behind the `affectedUsingTaskInputs` future flag.
       - A shallow clone marks every package as affected.
     - **Pros:** Free and deterministic. Already in your stack.
     - **Cons:** Package granularity only. Every Roam change hits "all of Roam". It knows nothing about features.
     - **Fit:** Good as a first coarse filter, for example a `packages/ui` change flags the website.
  
  8. **Coverage-based test impact analysis: Datadog TIA, Bazel rdeps** — https://docs.datadoghq.com/tests/test_impact_analysis/how_it_works/ **[S]**
     - **What it is:** Collects code coverage per test and skips tests whose covered files did not change.
     - **Pros:** Precise.
     - **Cons:** Needs an existing automated suite with coverage. You mostly have manual or CDP flows, so it does not apply to UI regression lists.
     - **Fit:** Low for now.
  
  9. **ML or LLM selection from the diff: CloudBees Smart Tests (formerly Launchable), Meta Diff Risk Score, LLM+RAG selectors**
     - **Sources:**
       - Launchable docs **[S/M]**: https://docs.cloudbees.com/docs/cloudbees-smart-tests/latest/features/predictive-test-selection
       - Meta Diff Risk Score, Aug 6 2025 **[S]**: https://engineering.fb.com/2025/08/06/developer-tools/diff-risk-score-drs-ai-risk-aware-software-development-meta/
       - Medium post on LLM+RAG selection **[M]**: https://medium.com/@yurii.pushkarenko/smarter-regression-testing-with-llms-and-rag-no-agent-army-required-72dc40219cdc
     - **What it is:**
       - Launchable trains on failure history.
       - Meta's DRS is a fine-tuned Llama that scores incident risk and feeds test selection.
       - The RAG pattern gives an LLM the diff, a dependency slice, and a test index (names, descriptions, last failure), and gets back a ranked JSON list.
     - **Pros:** The LLM pattern works with no history and can reason in feature terms.
     - **Cons:** It is probabilistic and can miss tests. Launchable needs months of data.
     - **Fit:** The LLM-over-an-index pattern fits well, if the index is a **feature map**: feature → entry files and UI path → how to reach it.
  
  10. **Devin confidence scores** — https://cognition.com/blog/devin-2-1 **[S]**
      - **What it is:**
        - Devin rates its confidence (green, yellow or red) at the start, after planning, and when answering questions.
        - At low confidence it asks clarifying questions.
        - Green tasks were about twice as likely to produce a merged PR.
      - **Fit:** Apply a confidence score per test item: "I don't know how to reach this" means red, so ask the dev.
  
  **Classic test-list formats:**
  
  - **Gherkin / Specification by Example:** Given/When/Then, with Examples tables.
  - **Exploratory test charters:** Hendrickson's "Explore *target* with *resources* to discover *information*", plus scope, out of scope, risks, setup and data. https://www.kenst.com/exploratory-testing-charters/ **[M]**
  - **Traceability matrix (RTM):** Requirement ID, test ID, status, defect ID, coverage verdict. There is no standard set of columns; ISO 29119-3 does not prescribe one. https://www.autemos.com/en/blogs/traceability-matrix **[M]**
  
  ### Fields worth adopting, one row per test
  
  - **ID**, and **title** written in Given/When/Then form.
  - **Origin**, one of:
    - `acceptance` → the Done-When criterion it traces to (RTM-style link)
    - `regression` → the impacted feature, plus the reason: changed file, shared component, or affected package
    - `dev-added`
  - **Impact evidence**: the diff hunk or dependency path that triggered it. This is what lets the dev judge whether a regression item is relevant.
  - **Risk or priority**, from likelihood × impact (risk-based testing; Meta DRS).
  - **How to reach it**: setup, fixtures or data, entry path, driver (CDP, Playwright, unit).
  - **Reach confidence**: high, medium, or low. Low means ask (Devin-style).
  - **Expected result**, with the pass/fail oracle.
  - **Decision**: proposed, accepted, declined or deferred, plus who decided, when, and a short reason. Declined rows stay in the list (RTM status columns; Spec Kit's dated clarifications).
  - **Run status**: not run, pass, fail or blocked. Plus an evidence link (screenshot or log, Showboat-style) and a link to any defect.
  - **Not verified**: explicit, with a reason (Codex guidance **[U]**).
  - **Charter-style scope / out-of-scope** at the top of the list.
  
  ### When tests get generated
  
  - **Ticket or spec time**, before any code. Strongest consensus: VirtusLab, Spec Kit, Kiro, Beck's test list. Acceptance tests come from the requirements, so they are not biased by the implementation.
  - **Plan time.** Anthropic and Codex say verification belongs in the spec or plan ("end-to-end verification step", "Done when").
  - **After the diff.** Regression or impact selection can only be done well once the changed files exist (TIA, `--affected`, DRS).
  - **Implication:** generate the list in two passes. Acceptance items at plan time, approved by the dev. Regression items after the diff, approved before running. Allow appends during implementation, as Beck does.
  
  ### Patterns for "agent asks dev when unsure"
  
  - **Interview with AskUserQuestion before writing the spec** (Anthropic docs **[S]**; Thariq on X, Dec 2025, https://x.com/trq212/status/2005315275026260309 **[S]**).
  - **Capped, sequential questions with recorded answers** (Spec Kit `/clarify`).
  - **Confidence-gated questions** (Devin).
  - **"Question me first, challenge my assumptions"** (Codex).
  - **What is missing:** no source I found deals specifically with an agent asking "how do I reach this feature to test it". Reach confidence plus a recorded answer (fed back into the feature map) would be new. Treat it as a design choice, not established practice.
  
  ### Hype and caveats
  
  - **Weak sources:** Stripe Minions coverage (1,000+ agent PRs a week, deterministic test steps in its pipelines, InfoQ Mar 2026) is mostly secondhand. Claims from tool vendors like Quellit and Specship are marketing.
  - **Not covered:** I did not find primary posts from Ramp, Linear, Vercel, Graphite or Shopify on agent-generated test plans.
  - **Ralph loop "back pressure":** Huntley's idea that more automated checks allow more autonomy is persuasive, but it comes from talks and podcasts.

  ### D. How to run it in Obsidian
  
  **(i) In-app.** Inject core plus the overlay into the renderer and write an Obsidian in-page Executor:
  - `run`: port the executor but replace the palette with `app.commands.executeCommandById` or the `.prompt` palette.
  - `open`: `proof.obsidian.open`.
  - `check`: indirect eval.
  - `snapshot`: `.modal`, `.notice`, `.prompt` and active-leaf text.
  - `render`: bar and stage.
  
  Problems:
  - Synthetic input is untrusted. CM6 relies on `beforeinput`/DOM mutation and native selection, so `typeText` into the editor is unreliable.
  - tldraw needs real pointer events (my memory note `reference_tldraw_store_put_no_listener`).
  - Escape is caught by the modal keymap scope. Whether a synthetic keydown reaches Obsidian's keymap is unverified.
  - The Settings window is a separate renderer in 1.13, so an in-page runner can't reach it.
  - Outside fixtures (eng-2143-obsidian has two) can't run in the page.
  
  **(ii) Node-side (recommended).** machine.ts runs in Node unmodified, verified by the grep above: no window, document or localStorage. The Executor wraps the harness `client`:
  - `run`: inject `selector.ts` to resolve a selector into a visible, still rect, then send trusted CDP `Input.dispatchMouseEvent` and `key`/`typeText`. `open` and `command_palette` go through `client.evaluate`, and `js` goes through `client.evaluate`.
  - `check`: `evaluate` of `expect.js`.
  - `snapshot`: DOM text plus `client.screenshot()`. This finally makes the `screenshot` action real, which feeds pr-evidence.
  - `render`: `evaluate('window.__proofHud.paint(state)')`.
  - HUD: inject the bar and stage bundle once. Register `Runtime.addBinding({name:"__proofCmd"})`. HUD buttons call `__proofCmd(JSON)`, Node's `Runtime.bindingCalled` handler calls `machine.command("hud", ...)`. Re-add the binding after a plugin reload or page reload.
  - Outside fixtures run in Node through `publishSql` plus psql.
  - `vault`, the lock and delivery come from the existing `launch`, `deliver` and `claim` (bundle marker, bundleHash).
  
  Why (ii): it gives trusted input for CM6 and tldraw, reaches the Settings target, can take real screenshots, and has a Node host for SQL. It also matches how Sid's own recorder attaches over CDP.
  
  **What breaks in Obsidian, in either shape:**
  - **Settings window (1.13):** a separate target. Pick the target per action and drive it by DOM; CDP mouse input doesn't reach it.
  - **Escape keymap scope:** use `client.pressEscape` (trusted) or `proof.obsidian.closeModals` instead of a synthetic dispatch.
  - **`.modal` overflow:** it clips popovers, and the stage ring can sit under the modal. Put the HUD at the `body` level with a high z-index.
  - **tldraw canvas:** needs real pointer events, collapsed sidebars and a measured camera.
  - **Contested vault plugin directory:** keep the deliver marker check and the main.js hash before and after the run.
  - **Plugin reload:** `reloadPlugin` replaces the plugin but `window.proof` survives, so re-inject after `delete window.proof`.
