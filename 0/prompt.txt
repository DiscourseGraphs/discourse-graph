  ## How read-only is enforced
  **Postgres privileges, not RLS** — this is Design decision 3 and the first stated Goal: "Postgres privileges enforce read-only access, so a forgotten RLS check cannot let an agent write." Postgres refuses every write before RLS runs. The role lives in `auth.users.role`, which Supabase Auth copies into the `role` claim of every token (verified in `GenerateAccessToken`); only the admin API can change that column (`SetRole` is called only from `admin.go`); the custom access token hook is not enabled in this project.   Alternatives rejected for read-only enforcement: a custom claim checked in RLS (would need the check in every writing policy and all 27 `SECURITY DEFINER` functions, any miss lets an agent write); a `read_only` flag in RLS (same fail-open problem); signing our own JWTs with the principal's `sub` (Supabase Auth accepts such a token on `PUT /auth/v1/user`, so the agent could set the principal's password and escalate — `secure_password_change` is off in `config.toml`); signing JWTs with a non-user `sub` (needs an imported key and our own refresh endpoint); token exchange in Vercel functions (works, but every Supabase operation has to be re-implemented there — the earlier approach, block `((R660W1hbd))` "Restrict what you can do with the credentials").
  
  ## Revocation
  `revoke_agent_grant(agent_id UUID)`, a `SECURITY DEFINER` function granted to `authenticated` only. It deletes the `auth.users` row for the agent when a grant with that agent and `principal = auth.uid()` exists; the cascade removes the `agent_grant` row and Supabase Auth's own foreign keys remove the agent's sessions and refresh tokens. **Immediate**: `my_user_accounts()` reads `agent_grant` on every query, so an unexpired access token stops matching the principal's access on the very next query. `authenticated` has no direct `DELETE` on `agent_grant`, so revoking always removes the user too. Deleting the principal cascades the grant away and ends agent access the same way. A user cannot list or revoke another user's grants (RLS `principal = auth.uid()`). Fallback if the hosted `postgres` role can't delete from `auth.users`: move revocation to an Edge Function calling `auth.admin.deleteUser`.

  ## 1. Problem it solves (Proposal → Why)
  
  "Users need to retrieve relevant synced discourse nodes from their agent interface without opening Roam or Obsidian during retrieval or installing a platform-specific MCP for each." V0 exposes that collection through a documented direct API **and** an MCP, reusing existing graph/pseudo-user identities for setup.
  
  ## 2. What changes (v0 scope)
  
  - Four read-only operations over both interfaces: get a node, search nodes, discover node types, get discourse context. Setup + operations validated in **Claude Desktop, ChatGPT, and Codex**.
  - A **separate, revocable read-only agent credential** managed in the DG web UI. Entry starts in Roam or Obsidian via the existing group-management pattern: a temporary handoff token establishes the website session, where the agent user and final credential are managed. Same final credential for direct API and MCP.
  - Retrieval covers every synced node readable by the credential's graph/pseudo-user, **including accessible shared nodes never imported into the client**. Permissions follow current access live; revocation kills all access through that credential.
  - **Per-space credentials** are the working v0 identity model. Another space's synced-but-unpublished nodes need a separate credential; no promise of one credential spanning a person's spaces.
  - get-node returns node ID, title, type, full synced text body, source/provenance link. Attachment downloads and image/file contents excluded.
  - Search reuses existing semantic search and stored embeddings, including **Roam's title-plus-description embeddings**; no title-only re-embedding. Hybrid search (keyword indexing + reciprocal rank fusion) deferred. Results: ID, title, type, short excerpt, provenance link, ordered by relevance.
  - Search defaults to **10**, max **30**, **no pagination**, **no relevance cutoff** (weak matches returned). Empty = no eligible searchable nodes, not a relevance judgment.
  - Type discovery over currently readable nodes; optional filter of one or more type IDs with OR semantics; omission searches all types.
  - Discourse context = incoming + outgoing **one-hop explicit** discourse relationships, with relationship type/direction and connected node ID/title/type. Both endpoints must be readable. Ordinary backlinks excluded.
  
  **Boundaries / known limitations:** candidate-node ingestion, general non-discourse content, canvas functions, write-back, relation creation, candidate elevation, feedback capture, arbitrary-depth server traversal, and imported-only filtering are all out of v0 (agents may repeat one-hop calls). Unimported results may feel unfamiliar and must not imply local import membership. Semantic coverage follows existing embedding inputs, which differ by platform. Real-query evaluation examples and relevance thresholds deferred.

  ## 5. Numbered design decisions (8)
  
  **1. One retrieval service with two transport adapters.** Host direct API + remote MCP endpoint in `apps/website` on its existing Next.js server runtime. Add the MCP TypeScript SDK, pinning a version verified with all three clients. **Stateless Streamable HTTP**, request-scoped handlers, no in-memory MCP session affinity. Each adapter validates inputs, resolves the same credential, calls the same four server functions; shared response schemas and error codes; MCP returns structured results plus a compact text representation and marks all tools read-only. MCP must not call the public API over HTTP in-server. *Alternative rejected:* a separate MCP service (duplicate deployment/authz); platform-specific MCPs (reintroduce the setup problem). Includes an ASCII architecture diagram: Roam/Obsidian → temporary handoff → web agent management → per-space agent grant; direct-API bearer token and MCP credential URL → credential verification → shared retrieval service → agent-scoped database reads.
  
  **2. Keep the temporary handoff separate from the final credential.** Agent-management destination alongside group management; reuse the short-lived handoff; **never put the platform's access or refresh token in the final MCP URL**. Management uses the authenticated website session, verifies it represents the chosen pseudo-user, supports create/list/revoke; the server derives the principal from the session — "a submitted principal ID is never authority to grant access." An agent grant stores ID, principal auth-user ID, agent auth-user ID, label, creation time, revoked time. Provision a **separate Supabase auth user** per grant, kept distinct from the principal. Issue a **high-entropy opaque final credential, displayed once**; store only its hash + grant ID. The agent's login secret lives in encrypted server-only storage with the key outside the database. The server can mint a short-lived Supabase session for the agent; the opaque credential is never passed to Supabase as a JWT. Don't persist a mutable refresh-token session across concurrent requests; renew via the agent login secret; cache only unexpired access tokens while still checking grant state every operation. Credential valid until revoked; replacement = new grant + revoke old. Revocation marks the grant inactive first, then disables the backing auth user, and **the database must reject the inactive grant even if a previously issued JWT is unexpired**. Provisioning failures leave no usable grant; orphaned auth users cleaned up. *Alternative rejected:* handing out the principal's session (exposes write privileges); a long-lived JWT alone (revocation would depend on expiry).
  
  **3. Proposed MCP connection uses a credential-bearing URL.** Direct API takes `Authorization: Bearer <credential>`; MCP takes the same credential in a connection URL, proposed as `https://<host>/api/mcp?key=<credential>`, and also a bearer header where supported. **Conflicting URL and header credentials are rejected**; both routes resolve to the identical grant, no union of credentials/principals. For URL-configured clients select no client-managed auth; authenticate at the DG endpoint on every request, validating before tool discovery and every tool call. Do not advertise an unimplemented OAuth flow and do not expose private tools anonymously. The doc is explicit that this is "a proposed application-specific credential transport, not verified standard MCP OAuth interoperability," citing OpenAI's authentication documentation (OAuth; ChatGPT cannot present custom API keys) as not establishing whether the credential-URL workaround is supported — and warns not to claim official support or public-directory eligibility from a successful private connection. URL treated as a secret: HTTPS only, no redirects that propagate it, no analytics on the endpoint, no raw request URLs in errors or logs, `Cache-Control: no-store` on authenticated responses and the credential display page; display/copy deliberately rather than navigating to it; redaction must cover hosting/proxy logs too. *Alternative:* OAuth is the standard client-managed route, not selected for v0 after the user's URL proposal; remains the redesign option and "need not imply personal accounts."
  
  **4. Delegate reads without delegating writes.** Create an **`agent_reader`** database role with explicitly allowed retrieval reads/functions and no membership in write-capable roles. A **trusted Supabase access-token hook** assigns the role to provisioned agent users from server-controlled grant data (cites Supabase JWT/access-token hooks docs; hook config must be tested locally and in the deployed project). Read-specific permission helpers resolve an agent's active grant to its principal and evaluate current space/group/resource access; keep writer/owner checks on the actual caller — **do not globally replace `auth.uid()` with the principal**; normal-user paths unchanged; grant mappings not editable by agents or caller-supplied metadata; **reject chained agent principals**. Audit every reachable table/view and function grant including inherited `PUBLIC` execution and security-definer functions — agent sessions must not reach sync/upsert functions, management functions, or `create_secret_token` (which would let them become a website management session). Don't assume a view applies the intended role's row policies; use fixed search paths for security-definer helpers and keep them narrow. Service-role authority only in isolated provisioning/management; retrieval queries execute as the agent; every DB operation checks the grant and current permissions in its query snapshot; **no authorization-result cache, no copied group membership, no cross-request result cache**. In-flight reads use their transaction snapshot; revocation denies subsequent operations without waiting for JWT expiry. *Alternative rejected:* service-role reads filtered in app code (every new query a possible bypass); copying the principal's permissions into an agent account (drifts after sharing changes).
  
  **5. Normalize discourse nodes from existing records.** `Concept.id` is the API node ID, schema concept ID is the type ID, both **serialized as decimal strings to avoid JS bigint precision loss**. Select node instances only (exclude schema and relation records). Join content by both space and local ID (local IDs are not globally unique). Titles from synced concept + direct content; bodies from the authorized `full` content variant using existing cross-app format conventions; return stored text/markdown, not rendered HTML. Preserve source links as text; don't fetch assets or mint storage download URLs. Provenance from the synced document URL or platform/space/local-ID metadata; a source link refers to origin and never claims the node exists in the caller's vault. A missing `full` variant is **not** a complete body: get-node returns `content_unavailable` while the node stays searchable and visible in discourse context. Missing provenance or unsupported full-content formats also produce explicit data-availability errors, never a fabricated link/body. Distinguish stored-empty body from a missing row; fixture validation must exercise these states for both platforms before release. Type discovery derives distinct schema IDs from readable node instances independently of embeddings; return only readable schema metadata; missing schema data is a sync/access-integrity error, not a permission bypass; **do not merge identically named types across spaces**. *Alternative rejected:* content IDs as node IDs (variants appear as duplicate nodes); client-local title lookups (break headless operation).
  
  **6. Reuse semantic vectors with a retrieval-specific query.** Embed the query server-side with `text-embedding-3-small` at **1536 dimensions**; authenticate before incurring the embedding request; reuse the provider integration internally — no client-submitted vectors, no second unauthenticated call to the existing embedding HTTP route. Add a dedicated read-only search RPC on the existing embedding table with cosine-distance ordering, leaving the existing RPC untouched for current consumers. The query: resolve readable discourse node instances and any selected schema IDs; join current non-obsolete usable embeddings for `direct` and `direct_and_description`, preserving stored input semantics including descriptions; where multiple eligible embeddings represent one node take its best similarity and return it once; sort by similarity desc with node ID as stable tie-breaker, then apply the limit — **authorization, type filtering and deduplication happen before the limit**. Do not copy the current threshold predicate or the Roam experiment's post-limit local filtering, and **do not replace the threshold with zero** since negative similarities remain eligible. No keyword indexes, hybrid fusion, or re-embedding. Nodes without a current usable embedding are absent from search but still eligible for get-node, type discovery and context. Embedding-provider failures are errors, not empty results. **Excerpts = first 300 Unicode code points** of available synced body text, falling back to the stored semantic input when full content is absent; excerpts are not evidence the query matched the body; both interfaces document this. *Alternative rejected:* calling the existing threshold RPC unchanged (violates the no-cutoff rule and loses results when type filtering follows its limit).
  
  **7. Resolve discourse context using named roles.** Find readable materialized relation instances incident to the node, explicitly filtering `is_relation` and excluding schemas. Use `reference_content` source/destination roles for direction — the derived `refs` array identifies candidates but does not encode direction and can include other references. Require the relation, relationship-type metadata, and both endpoints to be readable. Return each relation ID with type, direction and connected-node summary; preserve separate materialized relationships rather than deduplicating by labels; a self-link can produce both an incoming and an outgoing entry; no traversal beyond incident relationships, no ordinary-backlink expansion. Return complete one-hop results within the host's response budget; if it doesn't fit, return an explicit **`result_too_large`** error rather than silently truncating or inventing pagination — full node bodies use the same complete-or-error policy. A **proposed 1 MiB serialized response budget** is an implementation guardrail to validate against all three clients, not a relevance or latency target. *Alternative rejected:* expanding every ID in `refs` (exposes non-discourse references, loses direction); silent truncation.

  ## AUTH design, faithfully
  
  ### Credential model (Decision 2, `2j6D7mlp_`)
  - Two distinct credentials. Setup starts **inside Roam or Obsidian**, reusing "the existing group-management handoff pattern": a short-lived **temporary handoff token** establishes a website session for the graph/pseudo-user. The **final credential** is created there and is *distinct* from the handoff token. "do not place the platform's access or refresh token in the final MCP URL."
  - The final credential is **high-entropy, opaque, displayed once**; the server stores **its hash plus the grant ID, not the plaintext**.
  - An **agent grant** record holds: ID, principal auth-user ID, agent auth-user ID, label, creation time, revoked time.
  - Each grant gets its **own provisioned Supabase auth user**, kept separate from the principal even though it inherits the principal's readable collection. Its login secret is in **encrypted server-only storage with the encryption key outside the database**.
  - The server exchanges that login secret for a **short-lived Supabase session**; "the final opaque credential is never passed to Supabase as a JWT." No mutable refresh-token session is persisted across concurrent requests; only unexpired access tokens are cached, and "grant state [is checked] on every operation."
  - **Identity is per space** (Requirement: Per-space principal, `rZ4hSJ5sl`): a credential carries one graph/pseudo-user's access; another space's private synced nodes need a second credential. Explicitly "does not promise one credential representing a person's combined access across spaces." Shared nodes readable by the principal *are* eligible without local import.
  - Management is `create`, `list`, `revoke`, authorized by the website session; "The server derives the principal from that session; a submitted principal ID is never authority to grant access."
  - Rejected alternatives: handing out the principal's session (exposes write privileges); a long-lived JWT alone (revocation would wait on expiry).
  
  ### Who issues and validates (Decisions 1, 3, 4)
  - Both the direct API and a **remote MCP endpoint are hosted in `apps/website`** on its existing Next.js runtime, via the MCP TypeScript SDK, **stateless Streamable HTTP**, request-scoped handlers. "Do not have MCP call the public API over HTTP inside the server."
  - Transport: direct API takes `Authorization: Bearer <credential>`; MCP takes the same credential in a connection URL, proposed as **`https://<host>/api/mcp?key=<credential>`**, and a bearer header where supported. **Conflicting URL and header credentials are rejected**; both routes resolve to the identical grant, "no union of credentials or principals."
  - Validation happens "**before tool discovery and every tool call**"; for URL-configured clients, select *no* client-managed authentication. "Do not advertise an OAuth flow that is not implemented, and do not expose private tools anonymously."
  - Database side: a dedicated **`agent_reader`** role with explicitly allowed retrieval reads/functions and **no membership in write-capable roles**; a **trusted Supabase access-token hook** assigns the role to provisioned agent users from server-controlled grant data.
  - Permission helpers resolve an agent's active grant to its principal and evaluate *current* space/group/resource access. "Keep writer/owner checks on the actual caller; do not globally replace `auth.uid()` with the principal." Grant mappings are not editable by agents; **chained agent principals are rejected**.
  - Service-role authority is used **only** in isolated provisioning/management; retrieval queries execute **as the agent**. No authorization-result cache, no copied group membership, no cross-request result cache.
  
  ### Read-only enforcement
  - Requirement: Read-only shared credential (`fOHxvkQ12`): the same credential authenticates both interfaces and "MUST NOT authorize modification of nodes, relationships, sharing permissions, **or agent grants**, even when its principal has write permissions."
  - Enforced **at the database boundary**, not in application code. Rejected alternative: "Reading with service-role authority and filtering in application code would make every new query a possible access bypass." Also rejected: copying the principal's permissions into the agent account ("would drift after sharing changes").
  - Required grant audit (`9NrrSL1WS`): audit every reachable table/view and function grant including inherited `PUBLIC` execution and security-definer functions. Named prohibitions — an agent session must not invoke sync/upsert functions, management functions, or **`create_secret_token`** "to turn themselves into a website management session." Security-definer helpers need fixed search paths and narrow scope. "do not assume a view automatically applies the intended role's row policies."
  - Gate: "Keep issuance disabled until access and write-denial tests pass" — tests named are direct database calls as the agent, **forged grant mappings**, **revoked JWTs**, and regression cases for normal users.
  
  ### Revocation
  - The final credential is valid until revoked; replacement = create a new grant/credential and revoke the old one.
  - Order matters: "**Revocation marks the grant inactive first, then disables the backing auth user**; the database must reject the inactive grant even if a previously issued JWT remains unexpired."
  - Each database operation re-checks the grant and current permissions in its query snapshot; "In-flight reads use their transaction snapshot; revocation denies subsequent operations without waiting for JWT expiry." Denial applies across **both** interfaces (Scenario: Revoked credential across interfaces, `fkpHUzSK7`).
  - Permission drift without revocation: gaining access makes data eligible, losing it stops retrieval, and "replacing the credential is not required" (`YkfsvaLgP`).
  - Provisioning failures leave no usable grant; orphaned auth users are cleaned up.
  - Rollback (`vSnoXY5Sv`): disable new issuance and the retrieval endpoints, revoke issued grants, disable their auth users, **preserve the revocation records while any issued sessions could remain valid**, and "Do not roll back the grant checks or read-only role restrictions before invalidating those sessions."
  
  ### Credential-URL secrecy rules (`mOtd0ZBum`)
  HTTPS only; no redirects that propagate it; no analytics on the endpoint; no raw request URLs in errors or logs; `Cache-Control: no-store` on authenticated responses **and on the credential display page**; copy it deliberately rather than navigating to it in a browser; redaction must cover hosting/proxy logs, not just application logs. "Query strings are not inherently protected by choosing this transport."
  Diagnostic logs are limited to request ID, operation, internal grant ID, duration, result count, error category — "Exclude credentials, full URLs, query text, node bodies, and provider payloads. No read-history UI or auditing subsystem is added."
  
  ### Tool surface
  Four read-only operations, identical across both transports (Decision 8, `4eQ8jt5P9`):
  
  | Direct API | MCP tool |
  |---|---|
  | `GET /api/v1/nodes/{id}` | `get_node` |
  | `POST /api/v1/nodes/search` | `search_nodes` |
  | `GET /api/v1/node-types` | `get_node_types` |
  | `GET /api/v1/nodes/{id}/context` | `get_discourse_context` |
  
  MCP "marks all tools read-only", uses structured results plus a compact text representation, and shares Zod schemas and error codes with the API. Error codes: 401 for missing/invalid/revoked credentials; 404 `not_found` for both nonexistent and unreadable nodes; 409 `content_unavailable`; 422 `result_too_large`; 503 for database/embedding dependency failures; `invalid_request` for bad inputs. Limits default 10, valid 1–30, no pagination. "Do not turn failed queries into successful empty collections."
  Client support requirement (`1qkZbig89`): documented setup and all four operations working in **Claude Desktop, ChatGPT, and Codex**, with **Roam and Obsidian closed**, and "no separate platform-specific MCP for Roam versus Obsidian."
  
  ### Phasing / release gates (Migration Plan, `oYiTb5hC8` — numbered)

  ## 2. The handoff flow (exact)
  
  1. User runs a **"Connect MCP" command** in a plugin that is signed in as the space account, and **chooses a label** (example used throughout: `"Laptop MCP"`).
  2. A shared helper (to live next to `createLoggedInClient` in `packages/database/src/lib/contextFunctions.ts`) creates a **second Supabase client with `persistSession: false` and `autoRefreshToken: false`**, signs in with `signInWithPassword` using the space account email (`spaceAnonUserEmail`) + space password — i.e. a genuinely new `auth.sessions` row, not a copy of the plugin's.
     - Rationale given verbatim: "A persisting client would overwrite the plugin's stored session. An auto-refreshing one would rotate the refresh token after it was handed over and break the MCP."
  3. That new session calls **`register_mcp_session(label TEXT)`** (SECURITY DEFINER, granted to `authenticated`), which reads **`session_id` and `sub` from `auth.jwt()`** and inserts the registry row. So a caller can only ever register *itself* — "cannot plant a plugin's session ID in the registry so that it can later be signed out as an MCP."
  4. The helper then **discards the client without signing out**, and returns the **handoff bundle**: **Supabase URL, anon key, space ID, and the new session's refresh token** (exactly these four).
  5. The plugin **shows the bundle once**, with a copy button, and **stores no copy of the refresh token**. The plugin's own session is unchanged and not replaced in storage.
  6. The MCP ends up holding **only that bundle** — i.e. a refresh token for a dedicated space-account session. It refreshes to get access tokens. The bundle's original refresh token stops working "once the rotation grace period has passed" (rotation is on, `refresh_token_reuse_interval = 10`), so the MCP must persist every rotated refresh token or it loses the session after its first refresh.

  ## 3. The `mcp_session` table (exact columns)
  
  ```
  session_id UUID PRIMARY KEY REFERENCES auth.sessions(id) ON DELETE CASCADE
  account_id UUID NOT NULL          -- the space account
  label      TEXT NOT NULL
  created    TIMESTAMPTZ NOT NULL DEFAULT now()
  ```
  - RLS: `SELECT` allowed where `account_id = auth.uid()`. **No client gets direct `INSERT`, `UPDATE` or `DELETE`.**
  - The `ON DELETE CASCADE` removes the row when Supabase deletes the session, including on the MCP's own local-scope sign-out.
  - Purpose, stated explicitly: a session's ID "appears only in its own tokens, and `auth.sessions` does not record which sessions were handed to an MCP.   - Settled decision: "v0 grants the full permissions of the space account."

  ## 5. Revocation / sign-out and timing
  
  Three mechanisms:
  - **Per-session sign-out** (*proposed for immediately after v0, timing unsettled*): `sign_out_mcp_session(session_id UUID) RETURNS BOOLEAN`, `SECURITY DEFINER`, granted to `authenticated` only. Deletes from `auth.sessions` where `id = session_id` **AND** `user_id = auth.uid()` **AND** a matching `mcp_session` row exists; returns whether a row was deleted. An unregistered session ID → nothing is ended and the call reports nothing signed out.
  - **Self sign-out** (in v0 scope, requirement "An MCP can sign itself out"): standard Supabase sign-out with **local scope**; its registry row then disappears via the cascade.
  - **Emergency switch**: `signOut({ scope: 'others' })` — signs out every other session of the space account, including all plugin instances.
  
  **Speed:** revocation takes effect at the MCP's **next refresh**, which fails. Already-issued access tokens stay valid until they expire — **up to `jwt_expiry` = 3600 s (one hour)**. Listed as an accepted risk: "`jwt_expiry` could be shortened for all users if needed." Ending already-issued access tokens is an explicit Non-Goal.
  
  Rejected revocation options on record: (b) custom access token hook with a `revoked_at` column refusing tokens for revoked sessions — deferred, "kept for when restricted accounts need a token claim: the `mcp_session` table is the place it would read"; (c) `signOut({ scope: 'others' })` only.

  - Part 1 (settled, MAP 2026-10-31): turn on `secure_password_change`. Verified against `supabase/auth` at `a7e97d6` (2026-10-30), `UserUpdate` in `internal/api/user.go`: a nonce is required only when `session.CreatedAt` is >24h old, and a refresh does not create a new session so the clock starts at handoff and never resets; the nonce goes to the account email, which space accounts cannot receive. **So for the first 24 hours after handoff the MCP can still change the password.**
