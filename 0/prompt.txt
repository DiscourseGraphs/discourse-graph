  ## 2. New findings
  
  **N1 (Medium): a failed batch can leave rows in the skipped batches unsynced for good. Found while re-checking finding 2; it was introduced in 4f54e761, not by the delta.**
  
  Locations: syncDgNodesToSupabase.ts:641-673 (the batch loop stops at the first failed batch), :872-881 (relation filter), :227-240 (`getLastRelationSyncTime`), :181-192 and :400-425 (Content watermark and change detection).
  
  What happens:
  - Relation instances are picked by `(lastModified || created) > lastRelationsSync`. That watermark is `max(last_modified)` over the relation Concepts already in the DB.
  - Batch order follows `relations.json` order, not time. Each relation's Concept gets `last_modified = lastModified ?? created`.
  - So if any row fails at or after the first batch that holds relations, the batches after it are skipped. Relations written earlier, including the healthy rows of the failing batch (each row has its own subtransaction), raise the watermark. Skipped relations that are older than that watermark are then never sent again until they're edited.
  - No repair path catches them: `findRelationIdsMissingSchema` only finds rows that exist with `schema_id` null.
  - Nodes are different. A new node in a skipped batch has no `direct` Content, so it's detected as new and its whole row is sent again (the ENG-1791 repair). An existing node's content edit in a skipped batch is only re-detected if `mtime > max(Content.last_modified)`, so it can stay stale too.
  
  What's new compared with main:
  - On main all Concepts went in one call. A call error rolled everything back, and a failed row skipped nothing else, so healthy relation rows couldn't be stranded.
  - Content had the same weakness on main: `uploadBatches` threw on a call error, and `upsert_content` has no per-row EXCEPTION block. This PR adds a trigger for it: any Concept row failure, schema and relation rows included, now skips the later batches.
  - Roam doesn't hit this, because its batch carries no relation rows.
  
  This shows up on large syncs, such as a first sync with more than 200 Concepts where relations cross a batch boundary.
  
  The code follows the Decision ("as Roam sync does"), so this is a question for sid. Proposed default (a) needs no code change:

The sync picks relations and content edits by comparing against the newest row already in the database, so a relation, or an existing node's content edit, in a skipped batch that is older than a row written before the failure is not sent again until it changes. New nodes recover on the next full sync. Follow-up: ENG-XXXX."
  - File the follow-up with `dg-create-engineering-ticket`: full sync re-sends relation instances that are missing from the DB, the relation version of ENG-1791.
