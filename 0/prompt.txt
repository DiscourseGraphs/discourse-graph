  ## Findings: MCP tool output-shape changes, tool rollout, and versioning
  
  ### 1. What the MCP spec says (current revision 2026-07-28)
  Source: https://modelcontextprotocol.io/specification/latest/server/tools and https://modelcontextprotocol.io/specification/2026-07-28/changelog
  
  - **outputSchema and structuredContent.** If a tool declares `outputSchema`, the server MUST return conforming `structuredContent`, and clients SHOULD validate it. The spec also says a tool SHOULD return the serialized JSON in a TextContent block "for backwards compatibility". The spec does not say what a client does when validation fails; that is left to the implementation.
  - **What actually happens on a mismatch.**
    - TS SDK server (`McpServer`): checks `structuredContent` against `outputSchema` before sending, so the call fails on our side (https://ts.sdk.modelcontextprotocol.io/v2/servers/tools).
    - TS SDK client, v1.x `Client.callTool` (read in source): throws `McpError` with "Structured content does not match the tool's output schema", or throws if the schema exists but no `structuredContent` came back.
    - The client compiles validators from the last `tools/list`, so validation is only as fresh as that list (https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/v1.x/src/client/index.ts). The Go SDK returns the same failure as error -32602 (https://github.com/modelcontextprotocol/go-sdk/issues/386).
    - **What this means for us:** `outputSchema` is a hard contract. A shape change that doesn't update the schema surfaces as a protocol error, not as slightly different data.
  - **No initialize step any more.** 2026-07-28 removed `initialize`. `serverInfo` now goes in each result's `_meta` (`io.modelcontextprotocol/serverInfo`), clientInfo goes in each request, and there is a new `server/discover` RPC.
    - `serverInfo.version` is only for identification. Nothing in the protocol consumes it to negotiate tool versions.
    - The spec has **no per-tool versioning mechanism.** The only related guidance is the tool-name charset, whose examples include names like `DATA_EXPORT_v2`.
  - **Tool-list freshness.** `tools/list` results must now carry `ttlMs` and `cacheScope`. `notifications/tools/list_changed` is delivered over `subscriptions/listen` and immediately invalidates a cached list (https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching). Annotations stay hints that clients must treat as untrusted.
  - **Why list_changed doesn't help us.** For an npx stdio server, tool definitions are fixed in the installed code. They only change when a new process starts on a new package version. list_changed would matter only if we generated tool definitions at runtime, for example from a server-fetched manifest.
  - **How clients cache tool lists:**
    - **Claude Code** (docs): re-fetches the tool list on list_changed in interactive mode, keeps the old list if the refresh fails, and `/mcp` Reconnect drops the cached list (https://code.claude.com/docs/en/mcp). Several issue reports say list_changed is ignored, so behaviour likely depends on the version.
    - **Cursor:** forum reports say list_changed is ignored or regressed, and that a restart or an `mcp.json` edit is the workaround (https://forum.cursor.com/t/mcp-notifications-tools-list-changed-not-acted-on-mid-session/161459). Not officially documented.
    - **Codex and Claude Desktop:** I could not verify either. The only Codex item I found was a feature request for a refresh command (https://community.openai.com/t/mcp-server-refresh-for-codex-cli-please/1380449).
    - **Practical assumption:** tool definitions are frozen for the whole session.
  
  ### 2. Impact on the agent side
  Source: https://www.anthropic.com/engineering/writing-tools-for-agents
  
  - **Field names are a contract.** Skills, prompts, CLAUDE.md snippets, chained agents and user scripts reference names like `node.title` and IDs to pass to the next call. Renaming or removing a field breaks them silently. The agent improvises, and you get no error unless `outputSchema` validation catches it.
  - **Keep or rename the tool?**
    - If the meaning is the same and the change is additive, keep the name.
    - If the output contract breaks, prefer a new name (`get_node_v2`, or a better descriptive name) or an opt-in parameter such as `response_format`.
    - Swapping the shape under an unchanged name, with an unchanged description, is the worst case for agents and for cached tool lists.
  - **Article guidance that applies here:**
    - Return high-signal, natural-language fields, but keep the IDs needed to chain calls.
    - Offer a `concise`/`detailed` response format. This is a natural place for a second shape to live.
    - Use strict output models.
    - Write actionable error messages.
    - Re-run evals after any tool change.
  - **The `content` text matters too.** Many clients pass only `content` text to the model. If that short text summary changes, model behaviour can change even when `structuredContent` is identical.
  
  ### 3. Versioning patterns for clients you can't force-update
  - **Additive-only v1 and v2 alongside.** This is standard and fits our rule. A field change counts as breaking if it renames, retypes, removes, or changes nullability.
  - **Deprecation signals.** Use the `Deprecation` header (RFC 9745, structured-date value like `@1767225600`, plus a `Link rel="deprecation"` to docs) and the `Sunset` header (RFC 8594, HTTP-date): https://www.rfc-editor.org/rfc/rfc9745, https://www.rfc-editor.org/rfc/rfc8594.
    - Our MCP must log these headers itself, because nobody else will see them.
    - Once sunset, return a JSON body. 410 is appropriate. Avoid 426: it formally requires an `Upgrade` protocol header.
  - **Minimum client version.** Have the MCP send `User-Agent: dg-mcp/<pkg version>` or `X-DG-MCP-Version`.
    - The website can then measure which versions still call each route, which is how you decide when to sunset.
    - It can also reject versions that are too old with a structured "upgrade required" body.
    - The MCP then turns that body into an `isError: true` tool result whose text says "restart your MCP client so npx fetches the latest version". The agent can relay that message. An opaque failure would not be relayable.
    - **We should ship this header and handling in the very next release.** Copies installed before it can never be identified or told to upgrade.
  - **Server-side indirection.** Keep a stable path per tool, a backend-for-frontend route the MCP owns, and change what's behind it.
  - **Adapter in the MCP.** Map the new upstream shape to the old tool output.
  - **Stripe-style date pinning.** Each account is pinned to the API version from its first request, and a `Stripe-Version` header can override it. Internally the server keeps a chain of "version change" transforms that rewrite current responses back to older shapes, so one implementation serves every version (https://stripe.com/blog/api-versioning). For us the equivalent is: the MCP sends a compile-time `API-Version`, and the route transforms the response down to it.
  
  ### 4. Work breakdown for `get_node`: internal route to `api/v1/nodes/[nodeId]`
  
  **Caveat that applies to every strategy.** Once a published npm build calls `api/v1/internal/nodes/[nodeId]`, that route is effectively public API. It has unknown callers, can't be force-updated, and is bound by the same additive-only rule. Either treat `internal` as "MCP-only public" from day one (version it, document it, add the version header and metrics), or don't ship it in a public build.
  
  **(A) Server-side: keep the MCP's route and change the implementation behind it (no MCP release)**
  - **Touched:** the internal route handler, which calls the same service or query as the public route and maps to the old response shape. Shared Zod response schema (unchanged). Route contract tests: snapshot of the old shape plus a parse against the old Zod schema.
  - **Old installed copies:** nothing changes, provided the response stays a superset of the old one.
  - **How long the old route lives:** indefinitely, or until version metrics show no callers. It becomes the stable façade.
  - **Effort:** S. This is the default whenever the new route's data is a superset of the old.
  
  **(B) MCP release that calls the new route and adapts it to the existing tool output (tool contract unchanged)**
  - **Touched:**
    - Tool handler: change the URL and add an adapter from the new shape to the old one.
    - Zod: parse the new response with the public schema, then emit the old output schema. `outputSchema` stays the same.
    - Unit tests: adapter fixtures from real responses of both routes, plus an assertion that the output validates against `outputSchema`.
    - Integration test against the public route.
    - Changelog and a semver minor or patch npm release. No agent-facing doc change.
  - **Old installed copies:** keep calling the internal route. Nothing breaks, but they stay pinned to it.
  - **How long the old route lives:** until metrics show old versions gone. This needs the version header from section 3. Without it, the window is "forever, or accept breakage". Add Deprecation and Sunset headers to the internal route.
  - **Effort:** M, mostly adapter, tests and the sunset tracking. Fields the old shape has but the public route lacks must be derived or nulled, which can turn this into an L.
  
  **(C) MCP release that exposes the new shape (tool output contract changes)**
  - **Touched:**
    - Tool handler, plus a new `outputSchema` generated from the public Zod schema.
    - Tool description and the `content` text summary.
    - Ideally a new tool name, or `get_node` with an opt-in format parameter, so old agents and skills aren't silently broken.
    - Updates to every skill, prompt and doc that references the old fields.

    - Tests: schema conformance and description snapshot.
    - Major semver release with migration notes.

  - **How long the old route lives:** same as (B). Two tool contracts are now in circulation for an extended period.
  - **Effort:** L. The code change is moderate; most of the cost is documentation, skill updates and coordinating the communication.

  ## How MCP server updates reach users (checked against docs and source as of 2026-11-20)
  
  **Bottom line:** With `npx -y @discourse-graphs/mcp@latest`, current npm checks the registry on every launch and installs a new version if one exists. The update takes effect only when the client restarts the stdio process: quit and reopen Claude Desktop, use `/mcp` → Reconnect (or restart) in Claude Code, or restart Codex. Nothing tells the user an update exists. If you need to detect stale clients, your server has to do it itself.
  
  ### 1. npx / uvx mechanics
  - **(a) How the update arrives.** I read the current npm source (`workspaces/libnpmexec/lib/index.js`, npm/cli `latest`). Every manifest lookup runs with `preferOnline: true`, so npm revalidates the package metadata with the registry on each launch.
    - **`pkg@latest` (a tag):** npx resolves the tag and compares the resolved tarball with the copy in `~/.npm/_npx/<hash>`. If they differ, it installs the new version. This is the same in the v9.9.3, v10.2.0, v10.9.0 and current source.
    - **Bare `pkg` (no version):** in the npx cache it is treated the same way (`npxByNameOnly`). But if the package is installed in the client's working-directory project or globally, npx runs that copy, which may be old. npx docs: "Package names provided without a specifier will be matched with whatever version exists in the local project." So `@latest` protects you from an old `npm i -g` copy; a bare name does not. https://docs.npmjs.com/cli/v11/commands/npx
    - **Exact pin (`pkg@1.2.3`):** never changes. Updating means editing the config.
    - **Ranges (`pkg@^1`):** older npm could keep a stale cached match. Fixed Feb 2025 (commit 8461186). https://github.com/npm/cli/issues/7838
    - **Old reports:** the many "npx serves a stale copy" threads mostly concern npm 6/7 or ranges. https://github.com/npm/cli/issues/1935
    - **Cache key:** the `_npx` folder is a hash of the spec string, so `pkg` and `pkg@latest` get separate cache folders.
  - **(b) What the user does:** restart the client. Nothing else.
  - **(c) Speed and reliability:** the next launch after you publish. Not verified:
    - What happens offline. My expectation is that npm fails or falls back to its HTTP cache; I did not test it.
    - How long the npm registry's CDN keeps serving the old package metadata after a publish. A related `npm pack` stale-metadata bug was fixed in March 2026 (https://github.com/npm/cli/issues/9045).
  - **Costs:** every launch makes a network call, which adds startup time. Codex's default `startup_timeout_sec` is 10 seconds.
  - **Risk:** `@latest` delivers breaking releases instantly and you cannot hold users back.
  - **(d) Non-technical users:** good. Nothing to do beyond a restart.
  - **uvx:** reuses the cached copy "unless a different version is requested". `pkg@latest` refreshes the cache. If the user ran `uv tool install`, that installed version wins unless `@latest` is given. So for uvx, use `@latest` explicitly. https://docs.astral.sh/uv/concepts/tools/
  
  ### 2. When the update takes effect (all clients)
  The client starts the stdio process when it launches. A new version runs only after that process is restarted.
  - **Claude Desktop:** "completely quit Claude Desktop and restart it." https://modelcontextprotocol.io/docs/develop/connect-local-servers
  - **Claude Code:**
    - `/mcp` → **Reconnect** for one server.
    - `/mcp reconnect all` (needs v2.1.284 or later) retries all failed or unauthenticated servers, so I'm not sure it restarts a healthy one.
    - A `list_changed` notification refreshes tools only within the running process; it never swaps in a new binary.
    - `claude -p` runs pick up the new version on the next run. https://code.claude.com/docs/en/mcp
  - **Codex:** no reconnect command is documented. The desktop app has "Restart" and the IDE extension has "Restart extension".
    - Watch-out: `startup_readiness = "catalog"` lets a cached tool list satisfy startup while the server connects, so the tool list Codex shows can briefly be older than the running server. https://learn.chatgpt.com/docs/extend/mcp?surface=cli
  - **Cursor / VS Code:** not researched. Both have per-server restart controls in their MCP UI, but I did not confirm current details.
  
  ### 3. Claude Desktop extensions (.mcpb)
  - **(a) How the update arrives:**
    - Directory extensions "update automatically by default". Privately distributed `.mcpb` files must be "install[ed] manually". https://support.claude.com/en/articles/10949351
    - **Major change, current docs:** "Desktop extension listings in the directory are deprecated, and the directory no longer accepts MCPB submissions. To distribute a local MCP server through the directory, include it in a plugin." https://claude.com/docs/connectors/building/mcpb.md
    - So a new `@discourse-graphs` `.mcpb` would be a manual download. Every update means downloading the new file and double-clicking it again.
  - **How updates are signalled:** not documented for privately distributed files. Assume users are never told.
  - **(d) Non-technical users:** installing is the easiest of all options (bundled Node, settings form generated from the manifest). Updating is the worst.
  
  ### 4. Plugins (the new directory route; Claude Code is documented)
  - **(a)** You bump `version` in `plugin.json`, or omit `version` so users track commits. Users get the new copy through background auto-update or by running `/plugin marketplace update` or `claude plugin update`.
  - **(b) Watch-out:** auto-update is **off by default for third-party marketplaces**, and `marketplace.json` has no field to turn it on. Each user toggles it in `/plugin` → Marketplaces, or an admin sets it in managed settings.
  - **(c) Watch-out:** if you keep the same `version` string, users never get new commits.
  - **Partial lever:** a plugin's MCP config could still point at `npx …@latest`, which avoids depending on plugin updates for the server code.
  - https://code.claude.com/docs/en/plugins/host-marketplace.md
  - Not verified: whether Anthropic's official directory marketplace auto-updates by default.
  
  ### 5. Registries and catalogs
  - **Official MCP Registry:**
    - Still "in preview". It holds metadata only: `server.json` points at the npm package. Every publish needs a new, unique version string, and published entries cannot be changed.
    - Docs say it is "not intended to be directly consumed by host applications". Aggregators are expected to sync roughly hourly.
    - I found **no client that auto-updates from it**. Publishing helps people discover the server; it does not deliver updates.
    - https://modelcontextprotocol.io/registry/about, https://modelcontextprotocol.io/registry/versioning
  - **Docker MCP Catalog / Toolkit:**
    - Docker builds and signs local servers in the `mcp/` namespace. Teams can "control which server versions" they use through custom catalogs.
    - New listings appear within about 24 hours of approval.
    - The docs don't cover how image updates reach users (tags, pull behaviour). Unverified. https://docs.docker.com/ai/mcp-catalog-and-toolkit/catalog/
  - **Smithery:**
    - Its hosted services, CLI and SDKs **shut down on 2026-10-31**. It is now only a non-proxied directory, run by Arcade.
    - Don't build on it. https://smithery.ai/future
  
  ### 6. Remote (Streamable HTTP) servers
  - **(a)** You deploy, and every user is on the new code immediately. Anthropic lists "Centralized updates pushed to all users" as a reason to choose remote over MCPB (mcpb.md, link above).
  - **What clients cache:**
    - The tool list, until a `list_changed` notification or a reconnect. Claude Code keeps the last list if a refresh fails.
    - Codex can start from a cached tool list (see §2).
  - **(b)** At most a reconnect.
  - **(d)** Best fit, but it means running a hosted service with OAuth, which conflicts with your local session-state design.
  
  ### 7. Git-checkout installs
  Updating means `git pull`, `pnpm install` if dependencies changed, then restart the client. Speed depends entirely on the user remembering to do it. Fine for contributors; not workable for non-technical users. (No source needed.)
  
  ### 8. What other servers do
  - **Playwright MCP:** every client snippet uses `npx @playwright/mcp@latest`. https://github.com/microsoft/playwright-mcp
  - **Sentry:**
    - Its main offering is the remote `https://mcp.sentry.dev`.
    - Local use now goes through the Sentry CLI's `sentry mcp`.
    - `npx @sentry/mcp-server@latest` is labelled "Legacy". https://github.com/getsentry/sentry-mcp
  - **GitHub:**
    - Recommends the remote server first. The local server is a fallback for clients without remote support.
    - The local Docker image `ghcr.io/github/github-mcp-server` is untagged in the examples, with no update guidance.
    - Renamed tools keep their old names "as aliases for backward compatibility".
    - https://github.com/github/github-mcp-server
  - **Figma:** not verified.
  - **Update warnings:** I found **no** popular server with a built-in "you're out of date" warning or minimum-version check. Not found, not proven absent.
    - If you want one, a self-built option: the server compares its own version with the npm registry at startup and puts a notice in its `instructions` or tool results.
  
  ### Recommendation for `@discourse-graphs/mcp`
  - Keep `npx -y …@latest`. Never tell users to `npm i -g`.
  - Restart the client is the only user step; document it per client.
  - Keep the session-state file format backward-compatible across versions, because users jump to new versions with no warning and you can't hold them back.
  - Add a server-side minimum-version check, so a user who is behind gets told.
  - An `.mcpb` makes installing easier but makes updating manual. A plugin needs the user to turn on auto-update. A remote server is the only option where updates reach every user with nothing on their side.

  ## Remote MCP migration research (as of 2026-11-25)
  
  ### 1. What the MCP authorization spec requires (current revision 2026-07-28)
  - **Auth is optional.** The spec says authorization is "OPTIONAL". If an HTTP server does support it, it SHOULD follow the spec. stdio servers SHOULD NOT follow it and read credentials from the environment instead. https://modelcontextprotocol.io/specification/latest/basic/authorization
  - **What the MCP server itself must do:**
    - Serve Protected Resource Metadata (RFC 9728). This is a MUST.
    - Answer requests without a valid token with `401` plus `WWW-Authenticate: Bearer resource_metadata=...` (SHOULD also include `scope`).
    - Validate every token, and accept only tokens whose audience is the MCP server (RFC 8707).
    - Rule quoted from the spec: "MUST NOT accept or transit any other tokens."
    - Rule quoted from the spec: "MUST NOT pass through the token it received from the MCP client." For an upstream API, the server acts as an OAuth client with a separate token. https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations
    - Insufficient scope returns `403` with `error="insufficient_scope"`.
  - **What the authorization server must do:**
    - Implement OAuth 2.1.
    - Publish RFC 8414 or OIDC discovery metadata.
    - Publish `code_challenge_methods_supported`. Clients must refuse to proceed without it, and they use PKCE S256.
    - Rotate refresh tokens for public clients.
    - SHOULD return `iss` in the authorization response (RFC 9207).
    - Clients always send `resource=<canonical MCP URL>`.
  - **Client registration** (https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration):
    - Client ID Metadata Documents (CIMD) are now the SHOULD.
    - Dynamic Client Registration (DCR) is MAY and **deprecated as of 2026-07-28**. It stays for at least 12 months.
    - Pre-registration is the third option.
    - Clients try them in this order: pre-registered, then CIMD (if the auth server advertises `client_id_metadata_document_supported`), then DCR.
  - **Can our MCP forward the client's token to our API?**
    - Not as a passthrough to a separate API. The spec forbids it.
    - Two compliant shapes:
      - (a) The MCP route and `/api/v1` are one resource (same audience), and the tools call the API's handlers in-process.
      - (b) The token's audience covers both.
    - This is my interpretation of the spec text, not something it says explicitly.
  - **Static bearer or API-key headers** (no OAuth):
    - Claude Code: `--header`.
    - Codex: `bearer_token_env_var` / `http_headers`.
    - mcp-remote: `--header`.
    - Claude.ai/Desktop: `static_headers` only, and it is "Beta, for a limited set of organizations". It is set once by an org Owner, and Anthropic says to treat it as the organization's credential, not a person's. https://claude.com/docs/connectors/building/authentication
    - Every client refuses tokens in the URL.
  
  ### 2. Supabase as the OAuth authorization server
  - **Status:** still **beta**, available on all plans. Public beta since 2025-11-26 per the changelog, and I found no GA announcement. https://supabase.com/docs/guides/auth/oauth-server/getting-started, https://supabase.com/changelog/38022-oauth-2-1-server-capabilities-for-supabase-auth
  - **What it provides:**
    - Authorization code + PKCE, refresh tokens, OIDC discovery, JWKS.
    - Discovery at `https://<ref>.supabase.co/.well-known/oauth-authorization-server/auth/v1`.
    - Optional DCR (`allow_dynamic_registration`).
    - Public and confidential clients.
    - Asymmetric signing keys are recommended, and required for `openid`.
  - **CIMD:** not documented. An open community question about CIMD support had no Supabase answer. https://www.answeroverflow.com/m/1457226093818806343
  - **Resource indicators (RFC 8707):** not documented.
  - **Audience:** tokens carry `aud: "authenticated"` by default. Audience binding would have to be done with the custom access token hook.
  - **Consent screen:** we must host it. Supabase redirects to Site URL + `authorization_url_path`. The page calls `supabase.auth.oauth.getAuthorizationDetails`, `approveAuthorization` and `denyAuthorization`.
  - **Token claims and our existing hook** (https://supabase.com/docs/guides/auth/oauth-server/token-security):
    - Tokens include `client_id`.
    - The custom access token hook runs for **all** token issuance and can detect OAuth via `client_id` or `authentication_method` (`oauth_provider/authorization_code`).
    - So our hook could set `mcp_reader` and an `aud` for OAuth sessions, which would replace the `mcp_session` lookup. That last point is my inference.
    - RLS can key on `auth.jwt()->>'client_id'`.
  - **MCP guide:** exists at https://supabase.com/docs/guides/auth/oauth-server/mcp-authentication. It advises requiring user approval, monitoring registered clients, and validating redirect URIs.
  - **Known DCR bug:** custom redirect URI schemes like `cursor://` were rejected. https://github.com/supabase/auth/issues/2285
  - **Alternatives:**
    - WorkOS AuthKit: CIMD and DCR, both off by default. https://workos.com/docs/authkit/mcp
    - Clerk: CIMD went GA on 2026-09-17. https://clerk.com/changelog/2026-09-17-client-id-metadata-documents-ga
    - Stytch, Auth0, Descope: I did not check them this session.
  
  ### 3. Hosting Streamable HTTP on Vercel / Next.js
  - **`mcp-handler` 2.x** (https://github.com/vercel/mcp-handler):
    - Serves the 2026-07-28 spec **statelessly**. It falls back to stateless 2025-era Streamable HTTP, where GET/DELETE return `405`.

    - The `redisUrl`, `sessionIdGenerator` and `maxDuration` options are gone.
    - Usage: `app/api/mcp/route.ts` exports `createMcpHandler(...)` as both GET and POST. Any path works.
  - **Auth wiring** (https://raw.githubusercontent.com/vercel/mcp-handler/main/docs/AUTHORIZATION.md):
    - `withMcpAuth(handler, verifyToken, { required, requiredScopes, resourceMetadataPath })` returns spec-shaped 401/403 responses.
    - `protectedResourceHandler({ authServerUrls })` goes at `app/.well-known/oauth-protected-resource/route.ts`.
    - Tools read `ctx.http?.authInfo`.
  - **Timeouts:** with Fluid compute, Node functions default to 300 s. Hobby is capped at 300 s, Pro at 800 s (1800 s in beta). That is ample for our four request/response tools. https://vercel.com/docs/functions/limitations (page dated 2026-08-24)
  
  ### 4. Client support today
  - **Claude** (https://claude.com/docs/connectors/building/authentication):
    - One auth stack backs claude.ai, Desktop, mobile, Claude Code and Cowork. On Desktop you add remote servers through Connectors (custom connectors).
    - Supported auth: DCR, CIMD, Anthropic-held client credentials, `none`, and `static_headers` (beta).
    - Hosted callback: `https://claude.ai/api/mcp/auth_callback` (it may move to claude.com).
    - Claude Code uses its own CIMD and a loopback redirect on an ephemeral port, so the auth server must match `localhost`/`127.0.0.1` with the port ignored.
    - Claude uses CIMD only if the auth server advertises both `client_id_metadata_document_supported` and `none`. Otherwise it falls back to DCR, which with Supabase is our only path.
    - Discovery, registration and token endpoints get a 10 s limit (30 s for refresh).
    - Claude uses only the first entry in `authorization_servers`.
    - Egress range is `160.79.104.0/21`.
    - Plans: Free (one custom connector), Pro, Max, Team, Enterprise. https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp
  - **Claude Code** (https://code.claude.com/docs/en/mcp):
    - `claude mcp add --transport http <name> <url>`, then `/mcp` or `claude mcp login` for OAuth.
    - Supports `--header`, `--callback-port` and `--client-id`.
    - SSE is deprecated.
  - **Codex** (https://developers.openai.com/codex/mcp):
    - Configured with `url` in `config.toml`, plus `bearer_token_env_var` or `http_headers`, or `codex mcp login <name>` for OAuth.
    - `mcp_oauth_callback_port` pins the callback port; otherwise it is ephemeral.
    - Open bug: stale OAuth state in an already-open Desktop thread until restart. https://github.com/openai/codex/issues/29279
  - **ChatGPT developer mode** (https://developers.openai.com/api/docs/guides/developer-mode, https://help.openai.com/en/articles/12584461):
    - Auth: OAuth (CIMD, or DCR when configured), none, or mixed.
    - Without `offline_access` it can't refresh, and users must re-authenticate.
    - Tools without `readOnlyHint` are treated as write actions and need confirmation.
    - Eligibility conflicts: the developer docs say Plus/Pro/Business/Enterprise/Edu; the help center says Business/Enterprise/Edu, with admin-only enablement on Business.
  - **`mcp-remote`** (https://github.com/geelen/mcp-remote): still maintained. It bridges stdio-only clients and supports `--header`, `--header-file`, static OAuth client info and transport selection. Its own README says to drop it once a client supports remote OAuth servers natively.
  
  ### 5. How other vendors moved from local to remote
  - **GitHub:** remote server preview 2025-06-12, GA 2025-09-04 with OAuth or PAT. Both versions share one codebase, and the local server is explicitly kept as a fallback for hosts without remote support. https://github.blog/changelog/2025-09-04-remote-github-mcp-server-is-now-generally-available/, https://github.blog/changelog/2025-06-12-remote-github-mcp-server-is-now-available-in-public-preview/
  - **Notion:** the local repo is "no longer actively maintained or supported". Notion supports only the remote server and "may sunset" the local one, with no date given. https://github.com/makenotion/notion-mcp-server
  - **Atlassian:** remote server only. Its HTTP+SSE endpoint is deprecated and was kept until 2026-06-30. https://community.atlassian.com/forums/Atlassian-Remote-MCP-Server/HTTP-SSE-Deprecation-Notice/ba-p/3205484
  - **Sentry:** hosted server at mcp.sentry.dev, with mcp-remote and a stdio mode for self-hosted setups. https://docs.sentry.io/product/sentry-mcp
  - **Linear:** remote only (mcp.linear.app/mcp). I found no local predecessor.
  - **Common pattern:** run both for a while, put remote first in the docs, then stop maintaining local rather than removing it on a hard date.
  
  ### What we must build
  1. **A remote MCP route in `apps/website`** using `mcp-handler` 2.x behind `withMcpAuth`. It would be stateless, with no Redis, and its tools would call the `/api/v1` logic in-process, which avoids token passthrough.
  2. **The `.well-known/oauth-protected-resource` route.** Its `resource` must exactly match the MCP URL, and it should list only the Supabase issuer.
  3. **The Supabase OAuth server, enabled with DCR**, since Supabase has no CIMD.
  4. **A Next.js consent page.** This is the hard part, because users have no personal DG login. The page needs a way to sign the user in, for example a plugin-issued one-time code (as with `create_secret_token`) that signs in as the space account before approving.
     - Decision needed: does an OAuth grant belong to the space account, or do we introduce per-person identities?
  5. **Custom access token hook changes.** For OAuth tokens (`client_id` set), the hook should set `role=mcp_reader` and a DG-specific `aud`. `verifyToken` then checks JWKS signature, issuer, `aud` and `client_id`.
  6. **A consent-revocation UI** and monitoring of registered clients.
  7. **A transition plan.** Keep the npx stdio package as a fallback for a period, put remote first in the docs, and possibly offer `static_headers`/`--header` for clients without OAuth.
