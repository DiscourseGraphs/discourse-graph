  - It lives on the plugin as `plugin.relationsIndex`.
- **`utils/discourseLinkFrontmatter.ts`**:
  - `getNodeTypeIdFromFrontmatter` (`:6`)
  - `getEndpointIdsFromFrontmatter` (`:11-24`), which returns `nodeInstanceId` plus `importedFromRid`
  - `countDisplayableRelations({relations, isConfiguredType})` (`:32-42`), which leaves out tentative imports (`tentative === false`) and relations whose type is no longer configured
- **`utils/discourseLinkUtils.ts`**: `resolveDiscourseLinkTarget({plugin, linktext, sourcePath})` (`:21-58`) returns `{file, nodeType, relationCount}` or null. - **`countRelationsForFile(plugin, file)`** (`DiscourseContextPopover.tsx:12-22`) already takes a `TFile` directly, but it is private to the popover file.
- **Popover contents:** `RelationshipSection` / `CurrentRelationships` (`components/RelationshipSection.tsx:432-468`) load asynchronously through `getNodeInstanceIdForFile` and `getRelationsForFile`, starting from `activeFile: TFile`.

**Reusable given a `TFile`?** Yes. Everything under the link-resolution layer is independent of the UI and needs only `plugin` plus `TFile`. ## 5. What is tied to markdown/CM6 and would need pulling apart

- **Finding links:** `INTERNAL_LINK_RE` / `extractLinktext` over CM6 `visibleRanges`, and `a.internal-link` / `data-href` in the DOM. A canvas would find its node files differently.
- **Link resolution:** `resolveDiscourseLinkTarget` needs `linktext` plus `sourcePath`. It should be split into "link to `TFile`" and "`TFile` to `{nodeType, relationCount}`". `countRelationsForFile` in the popover repeats that second half and could share it.
- **Refresh:** `refreshDiscourseContextOverlaySurfaces` only visits `MarkdownView` leaves and CM6 editors. `plugin.refreshDiscourseContextOverlay()` and `registerDiscourseContextOverlayRefresh` would need a way to register other surfaces, or the canvas would subscribe to `relationsIndex.onChange` and `metadataCache "changed"` itself. The `ViewPlugin` detects changes by comparing `relationsIndex.getVersion()`; a React canvas can simply subscribe with `onChange`.
- **Popover dismissal and placement:**
  - Any document scroll outside the popover closes it, so canvas pan/zoom may count as a scroll or not.
  - The outside-click listener is in the capture phase on `document`, so a click on the canvas closes it.
  - Placement is `position: fixed` from the anchor's rect, so it won't follow the anchor while the canvas pans.
  - The badge's `mousedown` preventDefault exists to keep the CM caret from moving; on a canvas it may clash with shape selection and dragging.
- **Behaviour that belongs to one mode:** the Live Preview-only check (`editorLivePreviewField`), skipping embeds, walking the transclusion chain, and skipping `.modal-container` all apply only to markdown.
- **Badge:** it is plain DOM with Obsidian's `setIcon`/`setTooltip` and `createSpan`. It can be reused, but inside a React canvas it would need a ref or a small React equivalent. `onActivate({file, anchor})` is already an interface that doesn't care about the surface.</result>

## 3. Performance
- **Old canvas overlay:** mounted only after the first pointer-enter, and the setting was read once per render via `useMemo`.
- **Page overlay:** `Wrapper` uses `useInViewport` and shows a disabled "-/-" placeholder until the reference is on screen (`DiscourseContextOverlay.tsx:331-362`). Counts are fetched on mount, not on click.
- **Caching:** `getDiscourseContextResults` has a cache; it's bypassed with `ignoreCache` on refresh. `useDiscourseContextMutationRefresh` refetches when relations change, which keeps a closed popover's counts from going stale (L236-238).
- **Context tab:** loads only when a single node is selected, cancels in-flight results when the selection changes, and bypasses the cache only after a mutation (`refreshCount &gt; 0`, `CustomStylePanel.tsx:58-81`).
