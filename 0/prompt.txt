  ## 5. pnpm-monorepo limitation — forum thread 116176
  
  [forum.obsidian.md/t/bug-plugin-scorecard-linter-cannot-resolve-internal-deps-in-monorepos/116176](https://forum.obsidian.md/t/bug-plugin-scorecard-linter-cannot-resolve-internal-deps-in-monorepos/116176)
  
  - **Opened 16 Jul 2026 by Hesprs.** The scorecard's type-aware lint on a monorepo yields many false positives, mostly `@typescript-eslint/no-unsafe-*`: every flagged package depends on an internal workspace package, the scanner neither links nor builds those, so their exports resolve as `any`. Running `eslint-plugin-obsidianmd` locally is clean because deps are wired. Requested fixes: allow a `postinstall`-style command before linting, or silence warnings for unresolved packages.
  - **2 Aug 2026, jeffsteinbok:** same problem, asked for workarounds.
  - **2 Aug 2026, Hesprs:** reported on Obsidian's Discord too; says the team has an internal feature request to allow `postinstall` but "this FR is not yet implemented since the linter still reports false positives even with `postinstall`." Workarounds offered: commit compiled types, or rename `d.ts` files to `*.test.d.ts` so the ignore globs skip them.
  - **2 Aug 2026, jeffsteinbok:** committing types didn't help — those files also trigger warnings and can't be excluded.
  - **4 Aug 2026, Hesprs:** reiterated the `*.test.d.ts` trick.
  
  **Status: open. No staff reply in the thread; the internal FR is reported secondhand only.** The `*.test.d.ts` workaround is consistent with the ignore globs I read in `lint.ts` (`'**/*.test.*'`), which is good corroboration that the action and the directory scanner share this ruleset.
  
  **Direct bearing on the PR debate:** this is the same class of failure as the ignored `ensureUserDeps` return value in `runScannerEslint` (§3). In a pnpm monorepo with `@repo/*` workspace deps, scanner lint will run with unresolved internal types and emit `@typescript-eslint/no-unsafe-*` findings — which in the action's scanner config are mapped `"warn"`, so they land as warnings in both modes, but the upstream `obsidianmd/*` rules configured `"error"` would, with `strict: true`, fail CI on exactly this known-unfixed upstream bug. That is a concrete argument for `strict: false` until the monorepo resolution issue is fixed.
