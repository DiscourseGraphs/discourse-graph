  ## 1. Security — leading-whitespace bypass hands an `obsidian:` URI straight to the OS handler
  `apps/obsidian/src/components/canvas/utils/textShapeLink.ts:24-25` + `overlays/TextLinkOverlay.tsx:69-73`
  
  The allowlist uses `new URL(value)`, which **strips leading C0 controls and spaces**. `isObsidianUrl` uses a raw `startsWith` on the un-normalised string. They disagree:
  
  ```
  " obsidian://open?vault=Other&file=x"   // or "\tobsidian://…", "\nobsidian://…"
    isAllowedTextLinkUrl -> true   (URL trims; host "open", file present)
    isObsidianUrl        -> false  (" obsidian…".startsWith("obsidian:") === false)
  ```
  Verified with node: `new URL(" obsidian://open?file=x")` → protocol `obsidian:`, host `open`.
  
  Failure scenario: a user pastes (or a shared/synced `.tldr` carries) a text shape with `meta.url = " obsidian://open?vault=SomeOtherVault&file=…"`. `getTextShapeLinkUrl` returns it verbatim, the overlay renders it as `href`, the click handler's `isObsidianUrl` guard returns false so **`event.preventDefault()` is never called**, and the anchor navigates — Electron hands the `obsidian:` URI to the OS handler. That is exactly the outcome the comment on line 71-72 says it prevents, and it also bypasses the `resolveObsidianUrlToFile` cross-vault check (which is the only thing stopping a link from switching the reader to a different vault).
  
  Fix: make `getTextShapeLinkUrl` return the **normalised** URL (`new URL(value).toString()`, or at minimum `value.trim()`) so every downstream consumer sees one canonical form, and derive `isObsidianUrl` from `new URL(url).protocol === "obsidian:"` rather than a string prefix. Three different prefix tests exist today (`isObsidianUrl` lowercase `startsWith("obsidian:")`, `parseObsidianOpenUrl`'s `startsWith("obsidian://")`, and the allowlist's `URL.protocol`) — collapse them onto the parser.

  Same files. Two more consequences of the above:
